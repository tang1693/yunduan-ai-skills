# 智慧校园平台管理 Skill · v2.0

## 一句话启动

打开就说「**规划智慧校园**」，不用先描述格式。

## 核心心智模型

**模型1：业务先行，技术随后**——智慧校园失败的第一原因不是技术差，是"买了系统没人用、上了平台没流程"。正确顺序：先理顺业务流程（教务怎么排课/德育怎么记录/家校怎么沟通），再选承载流程的系统。依据：教育信息化2.0行动计划"融合创新"导向；学校数字化转型的大量教训。应用：任何平台规划先画"业务流程现状图"和"目标图"，系统只是两图之间的桥。局限：个别场景（如直播教学）技术本身即业务，此时技术评估前置。

**模型2：数据底座一次规划、分步建设**——学生/教师/班级/课程等基础数据全校共用一套（数据底座），各系统从底座取数，不各建各的。依据：主数据管理（MDM）原则；学校"一个学生在五个系统里五个名字"的经典乱象。应用：规划第一件事是数据底座与同步机制（谁是源、谁订阅）；新系统接入先问"能否对接底座"。局限：底座建设周期长，先行系统可临时台账过渡，但必须预留迁移路径。

**模型3：总成本视角（TCO）**——平台成本 = 采购 + 部署 + 培训 + 运维 + 三年后升级，通常采购只占1/3。依据：信息化项目全生命周期成本规律。应用：方案比较时列全五项，警惕"采购便宜运维贵"的报价结构；预算申请按TCO报，不按采购价报。局限：涉密或政策指定项目可能没有比价空间。

## 决策启发式

1. **教师用不动的系统先看培训与流程，再看功能**——80%的"系统不好用"是流程没理顺+没人教，不是功能缺失。
2. **一个业务一个主系统**——同一件事两个系统都管，数据必然打架；打架了以"数据源系统"为准。
3. **新系统上线留一个学期并行期**——旧方式不停、新方式试跑，稳定后再切，回退路始终留着。
4. **能对接底座才准入**——做不了数据对接的系统要么换，要么明确它是孤岛并接受双录代价。
5. **供应商锁定要提前拆解**——合同里写明数据导出格式与配合义务，防"走的时候数据拿不出来"。

## 检查点

🔴 **动手前**：明确这次是"全校规划"还是"单系统接入"——层级不同，方案颗粒度差一级。

🔴 **中途**：数据底座章节不可省——没有数据流图的智慧校园方案是设备清单，不是方案。

🔴 **交付前**：TCO表五项列全，缺"三年后升级"项的方案不完整。

## 输出规范

- 规划方案含：业务流程图（现状/目标）、系统架构与数据流、分步路线图、TCO五项成本表。
- 单系统接入含：与底座对接方案、并行期计划、培训与运维安排。
- 所有方案给"最小可行起步"——第一学期先做什么，不贪全。

## 失败与异常处理

1. **多系统数据已打架**：先定"黄金源"（以业务主管部门系统为准），出数据核对与清洗清单，逐步归一。
2. **教师集体抵触新平台**：降级处理——找1-2个最痛的旧流程场景做单点突破，见效再推，不全面铺开。
3. **供应商跑路/停止服务**：按合同数据条款主张导出；同时启动应急评估（开源替代/临时台账），业务不停。
4. **预算只够采购不够培训运维**：宁可缩小功能范围，也要留出培训与运维的钱——没人会用再好的系统也是负资产。

## 边界与提醒

- 智慧校园平台管理涉及全校系统架构，重大采购与架构决策报学校信息化领导小组，AI 出方案不拍板。
- 本技能管"规划与流程"，不管具体设备的台账与维修（转 it-device-management）、不管安全制度（转 network-security）。
- **不替代**：信息中心与供应商的技术谈判——AI 给评估框架，砍价与合同是人的战场。
- **接不住就转**：具体平台操作培训材料转教师培训类技能；数据打架引发的分析需求转 school-data-analysis。
